# scene — 场景结构设计方法论

## 定位

场景（SCENE）焦点类型的方法论文档。SCENE 是单个场域——一个时间×地点×POV 叙事切片的结构设计，不含正文。

对应三层链路：**章纲（structure）→ 场景（scene）→ 正文（chunk）**

每章由多个 SCENE 构成（通常 3-5 个），由章纲规划场域顺序。

## 何时加载

- FOCUS TYPE=scene 时自动加载

## 结构由脚本保障

content JSON 的字段结构由 `schemas.py` 自动校验：
- 子类型（开篇/推进/冲突/转折/展示/过渡/收束）必填
- POV角色、地点、一句话概要 必填
- 出场角色、核心冲突、关联情节线、字数 可选

你不必记忆字段清单——脚本会提示。

## 创作方法论

### POV 选择

- **POV 角色 = 这场谁在看**。读者的信息量与 POV 角色同步
- 切换 POV 时要有明确的分隔（空行/章节标记），避免读者迷失
- 同一章内 POV 切换不宜超过 3 个

### 一句话概要

用一句话回答：**在这一场中，发生了什么？**

好的概要：
- "林渊在练剑坪被苏长老指出天赋"
- "反派在密室策划对宗门的渗透"

差的概要：
- "林渊的日常"（不够具体）
- "各种事情发生了"（空洞）

### 核心冲突

每个场景至少有一个冲突——角色间的、角色与环境的、角色内心的。

- 冲突是场景的灵魂，没有冲突的场景应考虑合并或删除
- 冲突不必激烈——沉默、犹豫、克制也是冲突的表现形式

### 与前后的衔接

- **开篇场景**：从上一章结尾的情绪/事件自然延续，注明衔接点
- **收束场景**：为下一章留钩子或余韵

### 伏笔规划

伏笔不必全部兑现。支持四种回收方式：
- **精准回收**：明线伏笔明确兑现
- **落空**：读者预期的方向落空（反套路）
- **误解**：伏笔指向误导方向后揭示真相
- **悬置**：留待后续卷章回收

## 按子类型的方法论选型

`子类型` 参数决定了当前场域在章内的叙事功能：

### 开篇

章节的第一个场景，定情绪基调。

- 直接接续上章结尾，避免读者脱落
- 开场方式可选：动作开场 / 对话开场 / 环境切入
- 控制信息量，不在这时倾倒设定

### 推进

推动情节向前走，核心是释放新信息或制造新冲突。

- 每场推进一个具体情节节点
- 场景结束时比开始时状态有变化
- 字数紧凑，减少闲笔

### 冲突

正面对抗场景，核心是角色/势力之间的直接碰撞。

- 冲突前要做好铺垫——读者需要知道冲突的意义
- 冲突的结果应改变双方的力量对比或关系
- 避免为冲突而冲突

### 转折

反转或揭示场景，改变叙事方向。

- 转折需要前文的伏笔支撑，避免机械降神
- 同一场中只做一个转折
- 转折后应给读者重新评估前文的空间

### 展示

世界观/角色展示，不急于推进主线。

- 展示场景本身需要有独立的趣味
- 通过角色行动展示而非旁白说明
- 字数不限——好展示不怕长

### 过渡

衔接两个重点场景的桥接场域。

- 允许节奏缓冲和闲笔
- 侧重角色反应和内心世界
- 字数偏短

### 收束

章节的最后一个场景，留悬念或余韵。

- 收束方式：因果悬念 / 意象回落 / 闲笔余韵
- 为下一章做情绪上的铺垫
- 不要在这时引入全新的冲突
