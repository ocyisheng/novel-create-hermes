# 导入迁移指南（Agent 版）

本文档指导你（Agent）完成旧小说项目的导入迁移。你的核心优势是能够理解任何格式的文件内容——用户的项目可能用任何方式组织文件，你需要通过阅读内容来判断它们是什么、应该放到哪里。

---

## 总体流程

```
用户说"导入"
    ↓
init.py import 运行
    ├── 1. 复制源文件到 _migration_staging/
    ├── 2. 调用 classify_import.py（全量模式）
    │      ├── 分类每个文件
    │      ├── 自动路由到目标目录（移动/转换/拆分）
    │      └── 生成 migration_report.yaml
    │      失败 ↓ 回退
    │      └── 旧版文件名匹配路由 + 旧版 report 生成
    ├── 3. 后处理（仅新版成功时）
    │      ├── fix_yaml_indent（characters/ worldbuilding/ outline/分纲/）
    │      ├── validate_entity_consistency
    │      └── rebuild_project_index
    └── 4. 输出摘要（待审查数）
            ↓
你读取 migration_report.yaml
    ├── 处理 needs_agent_review 文件
    │   └── classify 判断 → convert 转换 → cp 到目录
    ├── 核验低置信度文件
    ├── 标准化（文件名、清 staging）
    ├── 更新 migration_report.yaml status → completed
    └── 完成
```

整个过程分两阶段：
1. **脚本阶段**（自动完成，你只需了解它做了什么）
2. **Agent 阶段**（你的工作——分类未知文件、验证自动结果、转换格式）

---

## 阶段一：脚本做了什么（了解一下就行）

`init.py` + `classify_import.py` 自动完成以下工作：

| 操作 | 说明 |
|------|------|
| 1. 复制文件 | 将源目录所有文件复制到 `_migration_staging/` |
| 2. 快速分类 | 对每种文件做初步分类（基于内容而非文件名） |
| 3. 三层转换 | 对能确定类型的实体类文件自动转换为标准三层结构 |
| 4. 多章拆分 | 对包含多个章节分纲的大文件自动拆分为独立文件 |
| 5. 生成报告 | 产出 `migration_report.yaml` |

**脚本能处理的情况**：
- 已是标准三层结构的文件 → 直接索引
- 含常见字段名（姓名/年龄/性格/世界名称等）的 YAML → 分类+转换
- 有对话/段落的纯文本 → 识别为章节正文
- 顶层 key 含 `第N章` 模式的多章节 YAML → 拆分

**脚本处理不了的情况**（这些需要你来做）：
- 字段名完全自创（全英文、拼音、缩写、编号体系等）
- 非 YAML 格式（JSON、TOML、纯文本笔记、Markdown 等）
- 混合内容文件（一个文件里既有角色又有大纲）
- 非常规的章节组织方式
- 脚本判断置信度低（< 0.7）的文件

## 阶段二：你的迁移工作流

这个阶段是迭代的，不是线性的。你可能会对一个文件反复操作多次——先粗分类，拆完后发现子文件需要重新分类，重组后发现需要再拆。**这是正常的。**

### 核心处理循环

```
                     ┌─────────────────────────────┐
                     │     1. 识别（Recognize）      │
                     │   读文件，理解它里面有什么     │
                     └─────────────┬───────────────┘
                                   ↓
                     ┌─────────────────────────────┐
                     │     2. 分类（Classify）       │
                     │   判断内容类型、定置信度      │
                     └─────────────┬───────────────┘
                                   ↓
                     ┌─────────────────────────────┐
                     │     3. 拆分（Split）          │
                     │   一个文件含多实体？拆开      │
                     └─────────────┬───────────────┘
                                   ↓
                     ┌─────────────────────────────┐
                     │     4. 重组（Restructure）    │
                     │   转换为目标目录结构和格式    │
                     └─────────────┬───────────────┘
                                   ↓
                     ┌─────────────────────────────┐
                     │     5. 标准化（Standardize）  │
                     │   三层结构、命名规范、对齐    │
                     └─────────────┬───────────────┘
                                   ↓
                          ┌─── 还有文件？───┐
                          │      是 → 回到 1 │
                          │      否 → 下一轮  │
                          └─────────────────┘
                                   ↓
                     ┌─────────────────────────────┐
                     │     整体验证                 │
                     │   读一轮目标目录，检查遗漏/   │
                     │   错误，发现则回到对应步骤    │
                     └─────────────────────────────┘
```

**每次迭代的粒度由你判断**：可以先对所有文件做一遍 1→2（识别+分类），拿到全局画像后再逐个做 3→4→5；也可以对每个文件一口气做完 1→2→3→4→5 再处理下一个。前者适合文件量大的项目，后者适合文件关系复杂的项目。

### 操作一：识别（Recognize）

读一个文件，理解它**实际上在表达什么**，而不是它叫什么名字。

| 文件名叫什么 | 可能是什么 | 但实际读完后可能是 |
|------------|-----------|-----------------|
| `角色设定.txt` | 角色 | 但读完后发现是世界观说明 |
| `大纲.yaml` | 大纲 | 但读完后发现是分纲 |
| `笔记.md` | 未知 | 读完后发现混合了角色+大纲+杂想 |
| `data.json` | 未知 | 读完后发现是结构化角色列表 |

**你比脚本强的地方**：脚本只能匹配预设字段名，你能理解语义。以下文件脚本都会判为 `unknown`，但你应该能读懂：

```json
[
  {"id": "P001", "name": "林默", "type": "主角", "stats": {"年龄": 24, "灵力": 95}},
  {"id": "P002", "name": "苏小小", "type": "女主", "stats": {"年龄": 19, "灵力": 70}}
]
```
这是一个角色列表，每项一个角色。

```markdown
> **力量体系**
> 武学九境：淬体、开脉、气海、神府、天罡、涅槃、虚空、造化、永恒
> 每境分前期、中期、后期、圆满四阶
```
这是世界观中的力量体系设定。

```yaml
volumes:
  - title: "初入江湖"
    chapters: [1, 30]
    summary: "林默走出新手村"
  - title: "风云起"
    chapters: [31, 60]
    summary: "各方势力登场"
```
这是分卷大纲。

**识别阶段的输出**：对每个文件，在心里形成一个判断——"这是一个关于 X 的文件，里面包含 N 个 Y 实体"。不一定要精确到字段，但要有一个整体认知。

### 操作二：分类（Classify）

基于识别阶段的认知，给文件一个明确的类型标签。

#### 类型体系

| 类型 | 含义 | 最终目标目录 |
|------|------|------------|
| `character` | 角色档案（一个人物的属性集合） | `characters/{名称}.yaml` |
| `worldbuilding` | 世界观实体（体系/势力/地理/文化等） | `worldbuilding/{名称}.yaml` |
| `outline_meta` | 总纲/故事框架 | `outline/总纲.yaml` |
| `volume_outline` | 分卷大纲 | `outline/分卷/卷N.yaml` |
| `chapter_outline` | 单章分纲 | `outline/分纲/卷N/第N章.yaml` |
| `plot_thread` | 情节线（主线/支线） | `outline/情节线/{类型}_{名称}.yaml` |
| `tracking` | 伏笔追踪/时间线 | `outline/追踪/{名称}.yaml` |
| `chapter_text` | 章节正文 | `chapters/第N章.txt` |
| `style` | 写作风格定义 | `styles/{名称}.yaml` |
| `unknown` | 以上都不是 | 暂存，标记，留给用户判断 |

#### 分类判断方法

你不是在查字段名，而是在回答一个问题：**"这段内容在故事创作中扮演什么角色？"**

**判断是不是角色** → 内容围绕"某个人"展开：
- 有一个人名作为核心
- 描述这个人的属性（年龄/性格/外貌/能力/背景/关系）
- 可以是结构化（YAML/JSON/表格）也可以是叙述性文字
- 关键信号：存在人物属性字段（不管叫什么名字），或大段的人物描写

**判断是不是世界观** → 内容围绕"某个体系/规则/世界"展开：
- 有体系名称或世界名称
- 描述规则、等级、分类、地理、势力、历史
- 内容本身不是在推进故事，而是在解释设定
- 关键信号：等级列表、规则清单、势力列表、地图描述

**判断是不是大纲/总纲** → 内容描述"整个故事怎么组织"：
- 故事结构（X幕/起承转合/四段式）
- 分卷列表
- 核心概念和基调
- 关键信号：有"卷"、"幕"、"部"等结构划分词

**判断是不是分纲** → 内容规划"某一章/某几章怎么写"：
- 有章节归属（"第X章"、"Chapter X"）
- 有情节点/场景列表
- 有出场角色标记
- 关键信号：结构化的事件序列+角色列表

**判断是不是章节正文** → 内容本身就是"故事叙事"：
- 连续段落，有情节推进
- 有对话
- 有场景和动作描写
- 关键信号：叙事结构（不是描述，不是规划，是在"讲"）

**判断是不是情节线** → 内容描述"一条故事线的演变"：
- 事件按顺序排列，跨越多个章节
- 有关联角色标记
- 关键信号：时间线上的事件序列

#### 多条类型同时满足怎么办

这种情况很常见，特别是用户的笔记式文件。**走拆分**——如果文件可以自然分成多个独立部分（比如前半段是角色，后半段是世界观），就在分类后标记为"需拆分"。然后在拆分操作中处理。

#### 置信度

给自己一个置信度：0-1.0。
- **≥ 0.9**：极其确定（标准格式或非常明确的内容）
- **0.7-0.9**：比较确定（内容指向明确但格式不标准）
- **0.5-0.7**：有点拿不准（似是而非，需要后续验证）
- **< 0.5**：别分类了，标记 review 留给用户

**置信度 < 0.7 的在后续迭代中优先核验。**

### 操作三：拆分（Split）

一个文件包含多个独立实体时，拆分为多个文件。

#### 哪些情况需要拆分

| 场景 | 例子 | 拆分策略 |
|------|------|---------|
| 一个 YAML 含多个角色 | `{林默: {…}, 苏小小: {…}}` | 每个角色一个文件 |
| 一个 YAML 含多个章节分纲 | `{第1章: {…}, 第2章: {…}, 第3章: {…}}` | 每章一个分纲文件 |
| 混合内容文件（笔记式） | 前半段是角色，后半段是大纲 | 按内容段落拆分 |
| 一个文件含多个世界观实体 | 力量体系和势力表写在一起 | 按实体拆分或保持一个文件（视内容量和耦合度） |
| 角色列表文件 | JSON 数组、YAML 列表、CSV | 每行/每项一个独立文件 |

#### 拆分原则

- **每个拆分出的文件必须是完整可用的**。不能是碎片——每个文件应该能独立支撑其用途（角色文件要完整描述一个人，分纲文件要完整规划一章）
- **保持内容完整性**：拆分时不要丢失信息。如果一个角色在源文件里分散在多处出现，先整合再拆分
- **拆分后的文件先放在暂存区**，等重组操作再路由到目标目录
- 拆分会触发**新一轮迭代**——拆出来的子文件需要回到"识别→分类→重组→标准化"流程

#### 不拆分的情况

如果多个实体高度耦合（例如"一个角色的档案同时包含他所属门派的世界观设定"，或者世界观的两个体系彼此依赖极深），可以保留在同一个文件里，路由到其主要类型的目录。

### 操作四：重组（Restructure）

把文件从原始格式转换为目标目录结构中的标准格式。这个操作包含两方面：**放对位置** 和 **格式转换**。

#### 路由规则

| 分类 | 目标路径 | 文件名 |
|------|---------|--------|
| `character` | `characters/` | `{角色名}.yaml`（从内容提取，不用原名） |
| `worldbuilding` | `worldbuilding/` | `{实体名}.yaml` |
| `outline_meta` | `outline/` | `总纲.yaml`（固定名） |
| `volume_outline` | `outline/分卷/` | `卷N.yaml` |
| `chapter_outline` | `outline/分纲/卷N/` | `第N章.yaml` |
| `plot_thread` | `outline/情节线/` | `{主线/支线}_{名称}.yaml` |
| `tracking` | `outline/追踪/` | `{名称}.yaml` |
| `chapter_text` | `chapters/` | `第N章.txt` |
| `style` | `styles/` | `{名称}.yaml` |

注意：**文件名不保留用户原名，使用标准命名**。脚本已经做了路由的文件，除非分类错误，不需要重新路由。

#### 格式转换

对实体类文件（character/worldbuilding/chapter_outline/plot_thread），转换为三层结构。转换的分工：

| 操作用 | 做 | 不做 |
|-------|--|-----|
| **脚本** | 已对含常见字段名的文件自动转换 | 不碰字段名自创的文件 |
| **你** | 对脚本无法处理的文件手動转换 | 不重复转换已是三层结构的文件 |

转换方法（看源文件格式灵活处理）：

```yaml
# 最终产物——标准三层结构
_meta:
  entity_type: "character"    # 实体类型
  schema_version: "3.0"
  created_at: "{当前时间}"
  updated_at: "{当前时间}"

索引信息:                      # 结构化元数据
  实体ID: "{唯一标识}"          # 建议用中文名
  名称: "{显示名称}"
  # 以下按实体类型选填
  角色类型: "主角/配角/反派"     # character 特有
  实体子类型: "体系/势力/地理"    # worldbuilding 特有
  章节号: 1                     # chapter_outline 特有
  情节线类型: "主线/支线"        # plot_thread 特有
  状态: "active"

摘要:                          # 关键信息摘要（供索引和快速查阅）
  一句话描述: "..."            # 核心一句话总结
  核心特质: ["特质1", "特质2"]  # 性格/特征关键词列表
  当前目标: "..."              # （角色、分纲选填）
  关键关系: [...]              # （角色选填）
  出场角色: [...]              # （分纲选填）
  核心情节点: [...]            # （分纲选填）

完整档案:                      # 源文件的完整原始内容
  # 保留用户原有所有字段，不裁剪、不改名
  # 用户在源文件里怎么写，这里就怎么放
  姓名: "林默"
  年龄: 24
  性格: "冷静、果断"
  # ... 任何用户自创的字段
```

**`完整档案` 的基本原则：保留原始内容，不做字段标准化。** 标准化的信息放在 `索引信息` 和 `摘要` 中，`完整档案` 是用户数据的"原样快照"。这样既保证了系统可读性，又不会丢失用户特有的信息结构。

### 操作五：标准化（Standardize）

最后一公里——确保所有文件符合项目规范。

#### 命名规范检查

每个文件的路由目标名是否符合标准？特别是：

- 角色文件：以角色名命名（`林默.yaml`），不是 `角色001.yaml` 或 `C001.yaml`
- 分纲文件：`第N章.yaml`，不是 `ch1.yaml` 或 `1-迷雾森林.yaml`
- 章节正文：`第N章.txt`，不是 `第一章.txt` 或 `ch1.txt`

如果用户源文件名有特定意义（比如分纲名为"第3章-迷雾森林.txt"），以标准名为主，**可以在 `摘要` 中保留原标题信息**。

#### 三层结构完整性检查

- 实体类文件是否都有 `_meta` + `索引信息` + `摘要` + `完整档案` 四部分
- `_meta.entity_type` 是否填写正确
- 章节号是否统一为整数（不是字符串 "3" 或 "03"）
- 时间戳格式是否一致

#### 跨文件一致性检查

- 分纲中引用的角色名是否与 `characters/` 目录下的文件名对应
- 分卷目录下是否有正确的分纲文件
- 同一卷的分纲是否都在同一目录下

#### 标准化中发现问题怎么办

**回到对应步骤重做**。这不是"一次过"——标准化阶段发现分纲引用了一个不存在的角色，需要回到识别/分类步骤找到这个角色的源文件，或者标记缺失。

---

### 循环终止条件

当你对 `_migration_staging/` 中所有文件**全部**完成了 5 步操作，并且**整体验证**（读一遍目标目录，随机打开几个文件确认）再没有发现问题时，循环终止。

## 迭代示例

以下展示一个典型项目的迁移过程，帮助你理解迭代是如何发生的：

**第一轮（快速扫描）**：
1. 识别全部 20 个文件 → 拿到整体认知
2. 分类 15 个文件（clear-cut），5 个不确定（标记 review）
3. 拆分明细的：1 个文件含 6 个角色 → 6 个独立文件
4. 重组 15 个 clear-cut 文件到目标目录
5. 标准化：检查命名、三层结构

**第二轮（处理遗留）**：
1. 重新识别标记 review 的 5 个文件
2. 其中 3 个现在能确定了（经过其他文件的上下文参照），2 个还是不确定
3. 拆出一个混合文件（角色+大纲+世界观 → 3 个文件）
4. 重组 3 个新确定的 + 拆分出的 3 个
5. 标准化：检查

**第三轮（整体验证）**：
1. 通读目标目录，打开关键文件
2. 发现：世界观文件引用了不存在的角色 → 回溯
3. 分纲文件缺少章节号 → 修复
4. 验收通过

## 类型判断快速参考

以下列出每种类型的内容特征，供快速对照：

### character（角色）
**内容在讲什么**：一个人。TA 是谁、长什么样、性格如何、有什么经历。
**格式无关的信号**：有人名 + 属性（年龄/性格/外貌/背景/能力/关系）。
**常见误判**：不要和"人物列表"混淆——列表通常需要拆分为多个单角色文件。

### worldbuilding（世界观）
**内容在讲什么**：规则、体系、势力、地理、历史——故事世界的"说明书"部分。
**格式无关的信号**：等级列表、规则说明、势力描述、地图、年表。
**常见误判**：不要和"角色档案"混淆——如果一段内容在讲"某个地方/某个体系"，不是"某个人"，就是世界观。

### outline_meta（总纲）
**内容在讲什么**：故事的整体框架——核心概念、结构划分、大局规划。
**格式无关的信号**：分卷列表、幕结构、核心冲突描述、故事基调。
**常见误判**：不要和"分卷大纲"混淆——总纲是全局的，分卷大纲是单卷的。

### chapter_outline（分纲）
**内容在讲什么**：某一章/某几章的具体规划——要写什么、谁出场、发生什么。
**格式无关的信号**：章节号、情节点列表、场景地点、出场角色。
**常见误判**：一篇很长的分纲可能被误认为章节正文——分纲是"规划要写什么"，章节正文是"已经写出来了"。

### chapter_text（章节正文）
**内容在讲什么**：故事本身——已经写出来的小说正文。
**格式无关的信号**：叙事体、对话、段落、场景推进。
**常见误判**：带很多对话的世界观说明（如"师父向徒弟解释力量体系"）——这种是叙事里的设定解释，不是世界观文件。判断标准：这段内容的主要目的是推进故事，还是解释设定？

### plot_thread（情节线）
**内容在讲什么**：一条故事线怎么展开——关键事件序列、关联角色。
**格式无关的信号**：事件序列（"第X章：发生了Y"）、主线/支线标记。

## 转换参考

### 章节号提取优先级

```
1. 文件名           → 第3章.yaml / ch3.md / Chapter_03.txt
2. 文件内标注       → "章节号: 3" / "chapter": 3
3. 内容首部         → "第3章 迷雾森林"
4. 无 → 顺序分配    → 按暂存区排序分配
```

### 卷号计算

```
卷号 = min(ceil(章节号 / 每卷章数), 总卷数)
每卷章数 = ceil(100 / 总卷数)
```

示例：总卷数 3 → 每卷 34 章 → 第 1-34 章在卷1，第 35-68 章在卷2，第 69-100 章在卷3。

### 文件名命名标准

| 实体 | 命名 |
|------|------|
| 角色 | `{角色名}.yaml`（不含特殊字符） |
| 世界观 | `{实体名}.yaml` |
| 分纲 | `第N章.yaml` |
| 章节正文 | `第N章.txt` |
| 情节线 | `{主线/支线}_{名称}.yaml` |
| 分卷大纲 | `卷N.yaml` |

## 脚本速查

迭代过程中的脚本操作参考。所有脚本都在 `.opencode/shared/` 目录下，通过 `python .opencode/shared/{脚本名}.py` 调用。

### 分类与转换（classify_import.py）

**全量模式**（脚本阶段已自动运行，迭代中通常不需要重跑）：
```bash
python .opencode/shared/classify_import.py \
    --staging-dir NOVELS_ROOT/项目名/_migration_staging \
    --project-root NOVELS_ROOT/项目名 \
    --volumes 3
```

**分类单个文件**——处理 unknown 文件时，先判断它是什么类型：
```bash
python .opencode/shared/classify_import.py classify _migration_staging/笔记.md
# 输出: {type: "character", confidence: 0.8, entity_name: "林默", ...}
```

**转换单个文件为三层结构**——确认类型后，将其转换为标准格式：
```bash
# 角色
python .opencode/shared/classify_import.py convert data.json \
    --type character --name 林默 --out characters/林默.yaml

# 世界观
python .opencode/shared/classify_import.py convert data.yaml \
    --type worldbuilding --name 天玄大陆 --out worldbuilding/天玄大陆.yaml

# 分纲
python .opencode/shared/classify_import.py convert chapter.yaml \
    --type chapter --name "第3章" --chapter 3 --out outline/分纲/卷1/第3章.yaml

# 情节线
python .opencode/shared/classify_import.py convert plot.json \
    --type plot_thread --name "天机令之谜" --subtype main \
    --out outline/情节线/主线_天机令之谜.yaml
```

### 文件验证（stage_verify.py）

**验证单个目标文件**——三层结构是否完整、编码是否正确：

python .opencode/shared/stage_verify.py --file characters/林默.yaml

### YAML 缩进修复（fix_yaml_indent.py）

在标准化步骤中批量修复 YAML 缩进格式，确保所有 YAML 文件缩进规范：
