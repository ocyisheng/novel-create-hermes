# novel-v2 — V2 创作引擎

项目已迁移到 V2（`graph/nodes.jsonl` 存在）时，本技能提供基于叙事单元网络的创作领域知识。

**结构字段由脚本保障**——`schemas.py` 在写入时校验必填字段，不需要你记忆字段清单。
**本技能只提供需要判断力的创作方法论。**

---

## 一、按焦点类型的创作方法论

### scene（写第N章 / 分卷大纲 / 分纲）

**场域设计：**
- 场域是基本写作单位。每章 3-5 个场域，每个场域是时间×地点×POV 的切片
- 切换场域 = 切换 POV 或时间或地点，进入/退出要自然
- 分纲中的场域规划包含：场域名、POV角色、持续时间、功能、氛围、节奏控制、进入退出方式

**张力曲线：**
- 不必追求完美抛物线。"不急欲观后文"才是书场真趣味
- 推进章追求效率，间奏章允许散漫闲笔
- 真正的速度感来自角色意志碰撞，不是外力强加的节奏表

**写作要点：**
- 前章衔接从同一场景/情绪自然延续
- 角色如果开始做你没想到的事：区分"文势所逼"（成长）与"粗暴干预"（突变）
- 语言尸体："暮色从四面八方袭来"是尸体，"光线从窗帘边缘挤进来"可能是观察
- 伏笔不必全部兑现。支持精准/落空/误解/悬置四种回收
- 章尾钩子不限于因果——可以是一个意象的回落

### character_arc（创建/编辑角色）

**扁平 vs 圆形：**
- 主角和关键配角必为圆形——标准：能否令人信服地让读者意外
- 功能性配角可用扁平——基于单一观念，易辨识易记忆
- 好小说需要两者。扁平人物注入作者活力后也可获得深度（狄更斯）

**自动性空间：**
- 角色被请进小说便有自身意志。如果角色开始反抗你的安排——通常是成功的标志
- 区分"文势所逼"（有内在逻辑的成长）与"粗暴干预"（突变）

**关系网络：**
- 使用开放式标签，不要用预设分类穷尽。贾宝玉与妙玉是"灵性上的共鸣者"
- 每条关系标注强度1-10和变化趋势

### plot_thread（情节/伏笔设计）

**伏笔四分类：**
| 类型 | 效果 | 场景 |
|------|------|------|
| 精准型 | 如约兑现，满足期待 | 冒险型支线、悬疑主线 |
| 落空型 | 预示但未发生，荒谬/讽刺 | 社会派心理向 |
| 误解型 | 读者/角色偏差，意外真实 | 多视角叙事 |
| 悬置型 | 开放式不回收 | 保持开放 |

**底层驱动力：**
- 故事驱动（"然后呢"）：悬念驱动，伏笔密度高按时回收
- 情节驱动（"为什么"）：因果驱动，伏笔可以有落空/误解型
- 因果律超出界限时人物沦为牺牲品

**复调结构：** 表面情节与反讽潜流并置。高大叙事/卑微现实形成反讽对照，支线作为主线的反讽镜像。

### world_rule（世界观建设）

**方法论选择：**
- 体系化建置（玄幻/西幻/科幻）：10个模板输出完整体系
- 笔记传统（现实主义/文艺向）：散点随笔，一点切入神韵全出
- 混合方案（多数长篇）：宏观架构体系化 + 微观细节笔记

**自洽性标准：** 判断标准是"在这个世界里它是否自洽"——不是在现实中是否可能。区分"开放区的矛盾"（刻意保留）与"粗心的矛盾"（失误）。

**延迟创建：** 核心设定早些完成，扩展设定写到需要时再补。

### note（总纲/叙事策略/灵感记录）

**总纲核心决策：**
- 人物与世界的关系：主角怎么进入世界？特殊在哪？规则怎么限制？怎么突破？
- 故事结构：三幕/五幕/自定义，每幕核心主线
- 节奏：前期/中期/后期基调，结局类型（开放式/圆满/悲壮/反转）

**叙事策略核心决策：**
- 视角：谁在看？第一/三人称？限制/全知？切换规则？
- 信息分配：哪些让读者先知道（戏剧反讽）？哪些藏到最后一刻？
- 笔法：冷笔（动作/紧张/信息）vs 热笔（情感/内心/氛围）

### chunk（质量检测/润色/修订）

**AI味道核心方法：** 逐句问"这个描述有写作者自己的观察角度吗？"能通用于任何小说的描述→语言尸体。

**情节逻辑：**
- 因果合理性 + 伏笔逻辑 + 结局必然性
- 因果律批判：情节是否过于"顺畅安全"？有没有"王后在花园里散步"式的破格？

**角色一致性：**
- 状态连续性：与上次出场时的状态是否连续（重伤→康复合理，重伤→正常跳跃）
- 自动性检测：角色完全按部就班→可能是提线木偶

**意志速度检验：** 慢节奏来自角色意志（好）还是啰嗦（差）？快节奏来自意志碰撞（好）还是仓促收尾（差）？

**润色原则：**
- 最小修改：只改问题，不附加"顺便优化"
- 保护修正痕：叙述者的自我纠正、记忆的不确定性是深度来源
- 保护起居注细节：不推进情节的生活细节可能是发明的核心
- 扁平化风险：修改后角色变得更可预测→如果是圆形人物，这是退步

## 二、QUERY 协议

写作过程中如果缺少信息，在回复中直接写入 QUERY 指令（编排层自动拦截并注入结果）：

```
QUERY: character_background(name="角色名")
QUERY: scene_detail(scene_id="场景ID")
QUERY: scene_detail(name="场景名")
QUERY: world_rule(name="规则名")
QUERY: plot_thread_summary(name="情节线名")
QUERY: plot_thread_summary()
QUERY: foreshadowing_status(id="F001")
QUERY: foreshadowing_status()
QUERY: style_check(text="待检查的文字")
QUERY: advanced_search(keywords=["剑","灵气"], limit=5)
QUERY: chapter_status(number=3)
QUERY: recent_context(chapter=5, limit=3)
```

**QUERY 指令不要出现在最终回复中——编排层会自动剥离。**

---

## 三、HARD CONSTRAINTS

1. **graph 是真相源** — 先写 graph，投影到文件是次要的
2. **按需查询** — 用 QUERY 协议获取缺失信息，不要一次性全量加载
3. **写后 flush** — 每次 task() 完成后 store.flush()
4. **记录 actor** — 所有操作传 `actor="novel-v2-crafter"`
5. **不要编辑 graph/ 下的 JSONL** — 通过 GraphStore API
6. **QUERY 指令不要出现在最终回答中**
