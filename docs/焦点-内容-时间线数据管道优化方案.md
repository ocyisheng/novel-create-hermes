# 焦点 → 内容 → 时间线：数据管道优化方案

> **状态**：设计提案  
> **日期**：2026-07-30  
> **关联模块**：WorkspaceBuilder、TemporalEventIndex、CharacterTimelineLedger、novel-v2-crafter、GraphStore  
> **涉及文件**：`workspace.py`、`temporal_index.py`、`character_timeline.py`、`handlers_graph.py`

---

## 一、背景

### 1.1 核心命题

V2 架构中，创作的基本单位是"焦点"（Focus）。用户每次操作都映射到一个焦点（SCENE / CHUNK / CHARACTER_ARC / PLOT_THREAD 等），系统围绕焦点预热上下文、驱动 LLM 生成内容、将内容写入 graph。

这个流程的完整链条是：

```
焦点 → 预热上下文 → LLM 生成 → 写入 graph
                                ├── content JSON（叙事内容快照）
                                ├── edges（实体间关系）
                                └── ???（时间线状态变化）
```

当前实现中，前两条路径（content、edges）是完整的、一等的操作；第三条路径（时间线状态变化）是**缺失的**——它被降级为"事后从 content 文本中反向解析"的补偿行为。

### 1.2 为什么这是一个问题

时间线维度（一个实体在故事时间轴上如何变化）和关系维度（一个实体在叙事网络中如何连接）是实体的两个正交维度。当前架构对这两个维度的处理能力不对等：

| 维度 | 写入方式 | 写入时机 | 数据精度 |
|------|---------|---------|---------|
| 关系（edges） | `graph.add_relation()` | 内容生成时立即写入 | 精确，无信息损失 |
| 时间线（TEMPORAL_EVENT） | 无自动写入 | 事后从 content 文本解析 | 有损，依赖文本质量 |

## 二、现状分析

### 2.1 数据流全景追踪

以用户说"写第3章"（焦点 = CHUNK）为例，完整的数据流动如下：

```
用户："写第3章"
  │
  ▼
编排层 → session.start(focus_type=CHUNK, id=chunk_003)
  │         session.build_workspace(level=warm)
  │
  ▼
WorkspaceBuilder.build("chunk_003")
  ├── _load_neighbors()       → 通过 edges 找到关联 SCENE / CHARACTER / PLOT
  ├── _load_type_specific()   → 从 SCENE.content 提取 time_text / location / cast
  │                               └── _sync_time_to_extra() ← 补偿钩子
  ├── _load_prev_next()       → 前后章节
  ├── _load_timeline_data()   → TemporalEventIndex.build() 全量扫描
  │                               ├── _extract_from_event_nodes() ← 扫 TEMPORAL_EVENT（通常为空）
  │                               └── _extract_from_content()    ← 从 content 文本反向解析事件
  └── _load_ego_graph()       → 关系图拓扑（edges）
  │
  ▼
LLM 生成内容
  │
  ▼
编排层/crafter 写入：
  ├── graph.update_unit(chunk_003, content="...正文...")   ← 写 content
  ├── graph.add_relation(char → scene, participates_in)    ← 写 edges
  ├── graph.add_relation(scene → plot, implements)          ← 写 edges
  └── ❌ 没有为任何实体创建 TEMPORAL_EVENT                  ← 缺失
```

### 2.2 断层的三个具体表现

#### 断层 A：写 content 但不写 extra.time

`_sync_time_to_extra()` 的注释直接承认了这个断层：

```python
# workspace.py:1402
# 同步 content["time_text"] → extra.time（弥补 crafter 只写 content 不写 extra 的断层）
self._sync_time_to_extra(scene_unit, content)
```

这个方法的逻辑是：当 `content.time_text` 有值但 `extra.time` 为空时，把文本标签同步过去。但它**只同步标签，不同步 ordinal**——因为 ordinal 应该在创建时确定，而不是事后推导。

#### 断层 B：三个互不知晓的 ordinal 分配逻辑

系统中存在三套独立的 ordinal 推导逻辑：

| 来源 | 位置 | 逻辑 | 触发时机 |
|------|------|------|---------|
| `_auto_ordinal` | `character_timeline.py:215` | chapter × 1000 + scene_order | CharacterTimelineLedger.build() |
| `_extract_from_content` | `temporal_index.py:235` | 从 content JSON 各字段提取 | TemporalEventIndex.build() |
| `_sync_time_to_extra` | `workspace.py:1467` | content.time_text → extra.time.label | workspace 预热时 |

三者之间没有协调机制。同一个场景在不同视图中可能得到不同的 ordinal 值。

#### 断层 C：TemporalEventIndex 全量扫描随数据量线性退化

当前 `TemporalEventIndex.build()` 每次调用都：

1. 遍历所有 `_units`（O(n)）
2. 筛选 TEMPORAL_EVENT 节点（O(n)）
3. 遍历所有 `_relations` 找 HAS_EVENT 边（O(m)）
4. 遍历所有非 TEMPORAL_EVENT 节点，调用 `_extract_from_content` 解析 content 文本（O(n × content_size)）

项目初期（几十个单元）没问题。故事推进到几百个叙事单元后，每次 build 的耗时会线性增长，且在大部分数据无变化时做了重复工作。

### 2.3 根本原因

```
根本原因不是"某个模块写得不好"。
而是：时间线状态变化没有被设计为焦点内容生成的原子产出。
```

焦点内容生成时产生的数据只有两个被明确处理了（content 和 edges）。时间线状态变化（角色突破、关系变化、物品转移等）被隐含在了 content 的文本描述中——例如 `cast[].role_status` 字段、`time_text` 字段。这些结构化信息没有被进一步处理为独立的时间线事件。

## 三、设计目标

### 3.1 核心目标

> **焦点生成内容时，时间线状态变化和 content、edges 一样，是一等产出。**

### 3.2 具体指标

| 指标 | 当前 | 目标 |
|------|------|------|
| 写 SCENE/CHUNK 时自动创建 TEMPORAL_EVENT | 从不 | 总是 |
| ordinal 分配方式 | 三套逻辑各自推导 | 焦点写入时由单一责任方确定 |
| TemporalEventIndex 构建方式 | 全量扫描 + 文本解析 | 增量索引，仅排序已存在的事件 |
| `_sync_time_to_extra` | 存在（补偿钩子） | 可删除 |
| `_extract_from_content` | 存在（文本回退） | 可删除 |
| crafter 生成内容后额外工时 | 0（不做） | 轻微（后处理解析） |

### 3.3 非目标（明确不改的）

```
✗ 不改 GraphStore（CRUD 能力已完整）
✗ 不改 WorkspaceBuilder 的结构（预热层次和加载策略没问题）
✗ 不改 session 模型（焦点生命周期没问题）
✗ 不改 novel-tool 接口（操作入口没问题）
✗ 不引入新的存储引擎（JSONL 够用）
```

## 四、优化方案

### 4.1 架构概览：补一条数据管道

核心思路是在"内容生成"和"时间线记录"之间补一条集中的数据管道，而不是给现有三个模块各加一个补偿逻辑。

```
┌─────────────────────────────────────────────────────────┐
│                     焦点内容生成                          │
│  (SCENE/CHUNK 写作 / CHARACTER_ARC 更新 / 等)            │
└─────────────────────┬───────────────────────────────────┘
                      │
                      │  crafter 完成 tool 调用后
                      ▼
┌─────────────────────────────────────────────────────────┐
│              事件抽取层 (EventExtractor)                  │  ← 新增
│                                                         │
│  职责：从刚写入的 content + edges 中提取实体状态变化，    │
│        创建对应的 TEMPORAL_EVENT 节点                     │
│                                                         │
│  输入：刚写完的单元 ID + content JSON                    │
│  输出：N 条 TEMPORAL_EVENT 创建操作                      │
└─────────────────────┬───────────────────────────────────┘
                      │
                      ├──→ TEMPORAL_EVENT 节点写入 graph
                      ├──→ HAS_EVENT 边写入 graph
                      └──→ ordinal 在此时确定并写入
                      │
                      ▼
┌─────────────────────────────────────────────────────────┐
│               TemporalEventIndex                         │  ← 改为增量
│                                                         │
│  职责：对已存在的 TEMPORAL_EVENT 排序 + 索引             │
│  不再：全量扫描 content 文本                             │
└─────────────────────────────────────────────────────────┘
```

### 4.2 新组件：EventExtractor

#### 位置

`shared/v2/event_extractor.py`（新文件）

或者更轻量：作为 `handlers_graph.py` 中 `handle_create_unit` / `handle_update_unit` 的**后处理钩子**（复用 hook 机制）。

#### 职责

在每次焦点内容生成/更新完成后，自动解析刚写入的 content，提取实体状态变化，创建 TEMPORAL_EVENT 节点。

#### 解析规则

根据焦点类型的不同，解析策略不同：

**焦点类型 = SCENE / CHUNK（场景写-作）**

```python
def extract_from_scene(unit_id: str, content: dict, store: GraphStore):
    events = []
    
    # 1. 场景本身作为时间线事件
    events.append({
        "event_type": "scene_event",
        "ordinal": _resolve_ordinal(content, unit_id, store),
        "time_label": content.get("time_text", ""),
        "summary": content.get("one_line_summary", ""),
        "location": content.get("location", ""),
        "characters": [c["name"] for c in content.get("cast", []) if isinstance(c, dict)],
        "precision": content.get("time_precision", "vague"),
    })
    
    # 2. 每个 cast 成员的状态变化（role_status 的变化）
    cast = content.get("cast", [])
    for c in cast:
        if isinstance(c, dict) and c.get("role_status") and c.get("name"):
            # 查找该角色上一次的状态，生成 state_before / state_after
            events.append({
                "event_type": "character_state",
                "ordinal": _resolve_ordinal(content, unit_id, store),
                "character": c["name"],
                "summary": f"{c['name']} 状态：{c['role_status']}",
                "state_after": c.get("role_status", ""),
                "state_before": _get_previous_state(c["name"], unit_id, store),
            })
    
    # 3. 场景中的关键事件（从 content 文本中提取的结构化事件）
    key_moments = content.get("key_moments", [])
    for km in key_moments:
        events.append({
            "event_type": km.get("type", "key_moment"),
            "ordinal": _resolve_ordinal(content, unit_id, store),
            "summary": km.get("description", ""),
            "characters": km.get("characters", []),
        })
    
    return events
```

**焦点类型 = CHARACTER_ARC（角色设定/弧光更新）**

```python
def extract_from_character_arc(unit_id: str, content: dict, store: GraphStore):
    events = []
    
    # 1. 能力/修为变化
    old = _get_old_content(unit_id, store)
    old_realm = old.get("能力设定", {}).get("修为") if old else None
    new_realm = content.get("能力设定", {}).get("修为")
    if new_realm and new_realm != old_realm:
        events.append({
            "event_type": "cultivation",
            "character": content.get("unit_name", ""),
            "summary": f"修为变化：{old_realm or '无'} → {new_realm}",
            "state_before": old_realm,
            "state_after": new_realm,
        })
    
    # 2. 性格/弧光变化
    old_start = old.get("character_arc_detail", {}).get("arc_start_state") if old else None
    new_arc = content.get("character_arc_detail", {})
    # ...
    
    return events
```

**焦点类型 = PLOT_THREAD（情节线更新）**

```python
def extract_from_plot_thread(unit_id: str, content: dict, store: GraphStore):
    events = []
    
    # 从 key_events 中提取
    for ke in content.get("key_events", []):
        events.append({
            "event_type": "plot_event",
            "ordinal": ke.get("ordinal", _approximate_ordinal(ke.get("chapter_number"))),
            "summary": ke.get("event", ""),
            "chapter": ke.get("chapter_number"),
        })
    
    return events
```

#### 集成方式

**方案 A（推荐）：编排层后处理钩子**

在 `operators`（编排层）的 crafter 调用完成后，增加一个 post-processing step：

```
crafter task() 返回
  ↓
编排层读取 crafter 写入的 content
  ↓
编排层调用 EventExtractor.extract(unit_id, content, store)
  ↓
编排层对每个返回的事件调用：
  graph.create_unit(TEMPORAL_EVENT, ...)
  graph.add_relation(entity → TEMPORAL_EVENT, has_event)
```

**方案 B（轻量）：GraphStore post_flush 钩子**

在 GraphStore.flush() 后自动触发——更自动化，但需要小心避免循环触发。

**推荐方案 A** —— 责任清晰，编排层显式控制，不隐蔽。

### 4.3 被简化/删除的模块

#### TemporalEventIndex：从"扫描+解析"变为"纯排序"

当前：

```python
class TemporalEventIndex:
    def build(self):
        self._extract_from_event_nodes()  # 保留
        self._extract_from_content()      # 删除（文本解析不再需要）
        self._rebuild_indices()           # 保留
```

改为：

```python
class TemporalEventIndex:
    def build(self, incremental: bool = False):
        if incremental and self._events:
            # 增量模式：只扫描自上次 build 后新增的 TEMPORAL_EVENT
            self._extract_new_events()
        else:
            # 全量模式：仅从 TEMPORAL_EVENT 节点加载
            self._extract_from_event_nodes()
        self._rebuild_indices()
```

`_extract_from_content()` 删除。所有时间事件只来源于 **TEMPORAL_EVENT 节点**。

#### `_sync_time_to_extra`：删除

这个补偿钩子的职责被 EventExtractor 取代。content → extra.time 的同步在 EventExtractor 创建 TEMPORAL_EVENT 时一并完成。

#### `_auto_ordinal`（CharacterTimelineLedger）：降级为回退

不再作为 primary ordinal 分配逻辑。只在 TEMPORAL_EVENT 节点没有显式 ordinal 时作为回退。

### 4.4 WorkspaceBuilder 预热时的增强

为了让 LLM 生成更精确的时间线数据，WorkspaceBuilder 预热时额外注入：

**注入内容示例**（以焦点 = CHUNK 为例）：

```
## 时间线上下文

当前故事时间位置：ordinal ~2300（第3章）
最近的事件：
  #2200 林渊到达落云宗外门 [scene_event]
  #2250 林渊通过入门考核 [scene_event]
  #2300 当前场景 ← 你在这里

涉及的角色当前状态：
  林渊：凡人（无修为），刚入外门 → 本章将要面对第一个修炼考验
  柳长老：外门管事，对林渊持观望态度

本章将产生的事件：
  场景事件：第3章正文（ordinal 2300-2500）
  角色变化：林渊 → 引气入体（如果本章涉及修炼突破）
```

这个上下文的生成逻辑：

```python
def _suggest_temporal_context(self, ws: Workspace, focus: NarrativeUnit, store) -> dict:

    # 2. 获取邻近事件
    nearby = TemporalEventIndex(store).build().query().around(ordinal, window=500).all()
    # 3. 获取涉及实体的当前状态
    # 4. 返回结构化上下文
```

## 六、迁移策略

### 存量数据兼容

Phase 3 删除 `_extract_from_content()` 前，存量数据中的时间线信息需要通过迁移脚本一次性转换为 TEMPORAL_EVENT 节点：

```python
# scripts/migrate_content_events_to_temporal.py
def migrate(store: GraphStore):
    """遍历所有存量内容，调用 EventExtractor 为每条事件创建 TEMPORAL_EVENT。"""
    count = 0
    for unit in store.list_all_active_units():
        if unit.type not in (UnitType.SCENE, UnitType.CHARACTER_ARC, UnitType.PLOT_THREAD):
            continue
        content = _parse_content(unit)
        if not content:
            continue
        events = EventExtractor.extract(unit.id, content, store, unit.type)
        for evt in events:
            # 检查是否已存在对应的事件（避免重复创建）
            if not _event_exists(store, unit.id, evt):
                _create_event(store, evt)
                count += 1
    return count
```

这个迁移脚本在 Phase 1 完成后即可运行，运行时不需要停服（TEMPORAL_EVENT 的创建是附加操作，不影响现有数据读取）。

### 回退策略

如果 EventExtractor 在某个边缘场景产生错误事件：

1. **删除事件**：TEMPORAL_EVENT 是独立节点，可直接删除
2. **降级回退**：TemporalEventIndex 保留 `_extract_from_content` 作为降级选项（通过配置开关控制）
3. **标记跳过**：EventExtractor 支持按单元 ID 黑名单跳过

```
4. 验证 HAS_EVENT 边被建立
5. 验证 TemporalEventIndex.build() 能正确索引该事件
6. 验证 WorkspaceBuilder 预热时能查询到该事件
```
